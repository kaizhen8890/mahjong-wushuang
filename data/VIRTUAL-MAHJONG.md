### 已实现并测试

- `tiles.ts`：每张牌独立 ID；四麻 136 张、三麻 108 张；赤五替换；宝牌循环映射。
- `wall.ts`：安全随机源和无模偏差洗牌；14 张王牌；4 张岭上牌、5 对表里指示牌；东家 14／其余 13；杠补牌时从牌山尾补入王牌，牌总数守恒。翻杠宝牌时机交给未来规则引擎，不由 UI 触发。
- `shanten.ts`：普通型、七对子、国士无双向听；结构听牌搜索；处理副露面子数量、已有副露导致的第五张牌排除。结构和牌不等于有役或可以合法和牌。
- `model.ts`：与旧 GameState 完全独立的牌／副露／牌河／玩家／规则／状态机类型；私有日志；Host 生成 AvailableActions 的接口。
- `projection.ts`：逐字段白名单生成玩家快照；只有本人的暗手牌和操作选项；不包含未来牌山、里宝牌、私有日志、对手暗牌／摸牌 ID、回应选择。预留无暗牌的旁观投影，不代表已实现观战联机。
- `call-window.ts`：合法选项 ID 回应、重复回应拒绝、全部回应或截止时间后仲裁；荣优先于碰杠，碰杠优先于吃；多家和／头跳／三家和流局仲裁。合法鸣牌选项仍需未来引擎计算，不能相信客户端传来的组合。
- `action-gate.ts`：动作封包基础校验、game/round/turn 拒绝旧请求、按已认证玩家与 actionId 去重、终止状态拒绝、可保存去重记录，换局清理。它不代替身份认证、规则校验或原子执行队列。
- `tests/virtual-foundation.test.ts`：以上模块自动测试，包括序列化后的隐藏信息检查、快照修改隔离和同时回应顺序。
- `rules.ts`：规则默认值及运行时校验；三麻默认 35000／40000，四麻默认 25000／30000。
- `scoring.ts`：复用现有 analyzeHand 和 calculateSettlement；自动宝牌／里宝牌／赤牌统计、无役拒绝、双倍役满开关、三麻支付、舍牌／临时／立直振听。传入上下文只能来自 Host 引擎，不能采用客户端手动勾选。
- `round-engine.ts`：MahjongRoundEngine 实验性单局流程，初始发牌、自动摸牌、摸切／手切、吃／碰、食替限制、立直／双立直／一发、荣和／自摸／多家和、九种九牌／四风连打／四家立直分支、荒牌流局、未听罚符；计时耗尽自动切合法牌、动作原子提交／失败回滚。现支持大明杠、暗杠、加杠、抢杠、岭上、杠宝牌和四杠散了；单局停止于ROUND_RESULT，对局管理层负责下一局。新增Host-only carry参数，只能初始化新局，不能恢复局中状态。
- `kan.ts`：Host 自杠选项、立直后暗杠验证。必须使用本巡摸到的第四张，等待集合相同，并验证所有原始和牌拆解都只能将原来的三张解释为刻子，不能只比较听牌种类。
- `match-progression.ts`：纯Host局数策略，庄家和牌／听牌连庄、途中流局连庄、轮庄、本场供托、南入西入、终局和排名。
- `match-engine.ts`：MahjongMatchEngine复用单局引擎；Host在局结果演出后调用advanceRound，带当前gameId和roundId防重复推进。下一局构造成功后才提交；跨局revision和私有事件sequenceId单调增加；终局冻结意图／tick／推进。
- `model.ts`／`projection.ts`：新增公开局结果；只有 ROUND_RESULT 才发送结果中的和牌者牌姿和允许公开的里宝牌，其他暗牌仍不广播。
- `shanten.ts`：新增 isComplete 专用结构检查，听牌／操作选项计算不再反复运行完整向听搜索，显著减少测试耗时。
- `tests/virtual-round.test.ts`：28 组单局／计分集成测试；加上基础 14 组共 42 组，均通过。新增 11 组杠相关固定局面测试，包括抢杠前不改牌／不翻宝牌、多人抢杠、超时、振听、立直后结构限制、四杠流局和荣和优先、三麻杠、最后活牌禁止杠。两种人数自动摸切至荒牌流局，校验牌数、唯一 ID、点数守恒和日志连续。跨局半庄由新增对局测试覆盖。
- `tests/virtual-match.test.ts`：14组，新增局数策略、三麻／四麻真实动作固定局面半庄、固定随机源逐张摸切半庄至西场终局、立直供托跨局、听牌连庄、剩余供托只发一次、换局失败可重试、旧动作拒绝、计时重置、飞点实际自摸、终局白名单。当前三份虚拟测试共56组。

## 现有模块复用边界

| 现有模块 | 虚拟模式用途 | 限制 |
| --- | --- | --- |
| lib/hand-analysis.ts | 牌姿拆分、役种、符数 | 立直、一发、海底、抢杠等上下文必须由 Host 推导；不使用手动勾选决定合法性 |
| lib/mahjong.ts 的 calculateSettlement | 番符点数、庄闲支付、本场和供托 | 已有 scoring.ts 适配双倍役满开关、三麻候选重排；单局引擎将供托只发给优先顺位和牌者一次；更多规则组合仍需测试 |
| lib/lan-native.ts + Android LanRoom | LAN 发现、连接、定向发送 | 虚拟协议独立命名空间；严禁对完整状态调用 broadcast |
| 现有实体 LAN hooks | 参考重连、计时和连接生命周期 | 不直接共用实体快照，因为实体模式不拥有隐藏手牌边界 |
| 现有 presentation/audio/表情机制 | 演出、播放器复用、发送节流 | 当前第三方表情和音乐不能直接作为虚拟模式原创素材；需逐项核实来源或替换，实体模式保留 |

旧 `lib/mahjong.ts` 中 `VirtualState` 仅是早期简易发牌功能，缺乏独立牌 ID、王牌和规则状态机；本模式不使用它作为权威状态。

## 后续实现顺序与验收门槛

1. **Phase 1 基础**：牌／牌山／状态模型／结构听牌／隐私投影已落地。规则运行时验证和基础结果类型也已增加；完整 Host 存档恢复验证仍未实现。
2. **Phase 2–3 完整单机规则（进行中）**：单局、杠系和对局生命周期检查点已落地。能通过Host推进下一局并进行自动半庄模拟，不等于全部规则组合认证。下一步优先完整Host checkpoint及恢复测试，补剩余规则边界。
3. **Phase 4 游戏牌桌**：实体／虚拟入口、手机横屏、自家底部大牌、六列旋转牌河、带来源副露、双击出牌、立直选牌与鸣牌组合选择。原创深靛蓝／金／朱红视觉，不能用 Dashboard 面板替代牌桌。
4. **Phase 5–6 LAN 与可靠性**：Host 同时参与；席位／准备／踢人／改规则；认证连接映射到玩家；重连 token；定向可见快照；动作队列原子校验与提交；Host 暂停后台策略；客户端只画状态、不算隐藏逻辑。
5. **Phase 7 演出**：接回立直、和牌、滚分、音效池和表情交互；新增发牌／摸切／鸣牌／翻宝牌短动画。只接入来源符合要求的素材。
6. **Phase 8 验收**：完整半庄自动模拟 + 规则专项测试 + 四台 Android 真机 LAN。通过之前不称作正式可玩版本。
7. **Phase 9 无双**：仅保留 GameMode 和未来接口，本阶段不自动执行技能卡自然语言效果。

## 安全与恢复约定

- 连接层必须先认证玩家；不能直接使用消息自带的 playerId 选择快照。
- Host 本机玩家也只向 UI 提供投影，不把完整状态塞进 React props；可信 Host 进程本身仍然可以接触全部牌，这是 LAN Host 信任模型的边界，不是防 Host 作弊方案。
- 快照没有原始 Event Log。以后需要演出通知时，建立单独的公开事件白名单。
- WAITING_CALL_RESPONSE 内收到回应可以更新 revision，但不能因此更换 turnId，导致其他合法回应变旧。
- 响应超时、主动放弃合法荣和必须更新振听；抢杠不能先不可逆修改副露或翻宝牌。
- 断线恢复由认证后的全量可见 Snapshot 完成；当前只有投影函数，尚无重连服务。
- RNG 注入只供 Host 测试；生产默认 crypto.getRandomValues，不允许客户端指定随机源。当前不实现 seed；未来若加 seed，只能进入 Host 私有记录。
- 存档需包含当局去重记录、计时状态、私有牌山和日志；客户端导出不得包含 Host 私有存档。当前 hostSnapshot() 仅用于测试／Host 调试，不是完整可恢复 checkpoint；pendingRiichi、firstCycleInterrupted、forbiddenDiscardTypes、pendingKan、rinshanPlayerId、lastNow、gate 仍在引擎私有字段里，恢复前必须补齐。
- 对局层的roundNumber、全局revision、history、terminal、初始庄家和时钟单调性状态也必须进入未来Host checkpoint。不可仅恢复单局再丢失对局层。当前carry不包含这些字段，不能充当恢复接口。

## 第四检查点的对局约定

- 起始庄家通过Host配置dealerSeat决定；同分以初始东→南→西→北顺序排序，三麻只使用前三席，后续轮庄不改变同分优先级。房间创建阶段以后可由Host随机选初始庄家。
- 庄家参与任一和牌（含多家荣和）则连庄，本场+1；闲家和牌轮庄，本场清零。荒牌流局本场+1，庄家听牌才连庄；途中流局本场+1并连庄。供托保留至和牌，最后未领取供托发给终局第一名一次。
- 新局继承点数、场风、局数、庄家、本场与供托；重新发牌并重置额外时间、立直、一发、振听、牌河、副露、杠状态和去重范围。新roundId拒绝旧局请求，Host推进也须匹配旧局ID。
- 新增rules.match：bankruptcy、dealerWinEnd、dealerTenpaiEnd默认为true，extension默认为one-wind。bankruptcy只在结算后点数小于0时触发，0点继续；关闭则允许负分继续。
- 末局庄家和牌／荒牌听牌且为第一并达到返点时，根据各自开关和了止／听牌止。庄家仍需连庄但不满足止局条件时继续。末局不连庄时，有人达到返点则结束；未达返点且开启延长时东风南入、半庄西入。
- 延长圈采用明确的项目策略：非途中流局结算后有人达到返点即结束；延长最后一局非途中流局结算后强制结束，即使庄家本可连庄。途中流局仍重打，不触发返点止局或延长上限。这不是声称完整复刻雀魂或天凤的全部终局变体。
- 最终排名展示原始点数、返点差、头名奖（oka）、顺位分（uma）与总成绩。总成绩=(点数-返点+oka)/1000+uma；oka=(返点-起始点)*人数，仅第一名获得。uma默认全0，可配置与人数匹配、和为0的整数数组，不提前替用户选顺位奖惩。
- MATCH_RESULT保持最后一局赢家的合法公开牌姿，但不公开输家的暗手牌、私有日志或未授权里牌。所有终局/规则字段继续逐字段投影。
- 新局生成失败不会替换旧局结果，允许Host稍后重试。advanceRound目前是Host编排接口，不是任意客户端可直接调用的操作；房间准备／结果确认交互待UI和LAN阶段接入。

## 第三检查点的杠规则约定

- 大明杠使用现有弃牌回应窗口，荣和优先。暗杠／加杠使用 `KAN + optionId` 意图；Host 根据自己的选项创建抢杠窗口，客户端不能传副露内容。
- 加杠允许普通合法荣和；暗杠只允许国士无双抢杠。当前为明确的项目默认约定，还没有房间切换项；不是照搬 WRC 的禁止国士抢暗杠。
- 宣告自杠立即打断首巡和所有一发；抢杠结束前不改手牌／副露，不补岭上，不翻指示牌。被抢后保留原副露，和牌牌仍由来源玩家持有，结果中公开引用它，牌张不重复转移。
- 三种杠均在无人抢杠／荣和、杠成立后补岭上，并在下一次操作提示前立即翻新宝牌。暂不实现明杠延迟翻宝牌变体。每杠移入一张活牌补足 14 张王牌；无活牌或已补四次时不允许再杠。
- 四杠分属多人且开关开启时，允许第四次岭上自摸及之后弃牌被荣和；无人荣和则四杠散了，不再接受吃碰。四杠归一人可继续，不允许第五杠。关闭开关时四杠不途中流局。
- 立直后暗杠采用严格牌形不变约束。依据 [WRC 2022 第 8.9.1 节](https://www.worldriichi.org/s/WRC_Rules_2022_20220708_site.pdf) 的结构约束进行核对；这里只采用这一约束，不据此更改本项目其他规则。
- 当前三麻北风仍按普通字牌处理，没有拔北意图或拔北计番。未来补独立拔北策略，不能将现状宣传为完整线上三麻规则。
- 可见快照现在提供回应来源、宣告种类及该公开牌的白名单字段；不提供其他人的暗牌、选项、回应、里宝牌或完整窗口。
- KAN 私有日志带 `stage: declared/completed`；大明杠在弃牌窗口决议后记录 completed。日志仍不是可独立重建完整状态的 Event Sourcing 实现。

## 规则参考边界

核对了 [WRC 2022 规则原文](https://www.worldriichi.org/s/WRC_Rules_2022_20220708_site.pdf) 的食替、振听及立直宣言相关章节。这里不是 WRC 赛事规则的完整实现：用户要求的多家和、赤牌、途中流局和立直须有 1000 点／剩余至少 4 张等采用本项目规则组合，不自动随 WRC 新版改动。后续杠规则尤其不能默认照搬 WRC 的“国士也不能抢暗杠”，须选定并记录虚拟模式的具体约定。
